# 秘书协作门禁流转规范

> version: v0.4（新增 §2.2 评审版本仲裁与审查范围分级 · Ref: #14）
> module: zhuanyemishutuan · docs
> Ref: #1 · PR #2 · #14

## 1. 目的

明确定义秘书团「开发 → 评审 → 测试 → 合并前最终评审」的门禁流转规则，替代早期「评审通过即接力测试」的不闭环流程。
v0.3（Ref: #14）为门禁往返加**上界**：轮次预算 + 非必要修复最多 1 次 + 停滞感知 + 静默交接不唤醒（§2.1）。
v0.4（Ref: #14）补**评审写回机制**：只在开启评审时记版本 + 防同写锁 + 延迟重试 + 单冲突收口（§2.2），
并加**审查范围分级**——日常只审变化、全量只在大版本（§2.3）。

## 2. 门禁流转（v0.2 新机制 · v0.3 加熔断上界见 §2.1）

```
┌──────────┐     发现问题/缺陷      ┌──────────┐
│ 秘书·开发 │ ────[回转]────────▶ │ 秘书·评审 │
│          │ ◀───[返工修正]──────── │          │
└──────────┘                      └──────────┘
     │ ▲
     │ │ 开发自评OK
     ▼ │ 只有确认无问题才接测试
┌──────────┐     发现缺陷      ┌──────────┐
│ 秘书·测试 │ ───[回转]─────▶ │ 秘书·开发 │
└──────────┘                  └──────────┘
     │
     │ 测试通过
     ▼
┌──────────┐    合并前最终评审     ┌──────────┐
│ 秘书·评审 │ ◀──────────────────── │          │
└──────────┘                       │ 合并放行 │
                                   └──────────┘
```

### 核心规则

1. **评审发现问题 → 回开发修正**（不直接放行接测试）
2. **开发修完、自评无问题 → 才接测试**
3. **明知还有问题 → 不接测试，回开发调整**
4. **准备合并之前 → 走最终评审放行**

## 2.1 循环熔断（v0.3 新增 · Ref: #14）

门禁往返本身也需上界，否则「打回 → 修正 → 复评」会无限循环。三道（+1）上界：

| 上界 | 默认 | 口径 |
|---|---|---|
| 门禁修复轮次 | 3 | 🔴 必修项回转为一次修复；耗尽即熔断 |
| **非必要修复轮次** | **1** | 🟡 建议项**最多修 1 次**；再报同类**不作回转**，改**结转登记** |
| 修复总轮次 | 5 | 防 🔴/🟡 交替出现绕过前两道 |
| 停滞重复 | 2 | 同一整改项指纹连续出现 2 次且无进展 → 判停滞循环，立即熔断 |

**判定顺序**：已熔断 → 停滞 → 总轮次 → 门禁 → 非必要 → 无需修复（`clear`，不耗预算）。
`clear`（既无 🔴 也无 🟡）不消耗任何预算、不唤醒。

### 熔断后：静默交接（不唤醒）

- 交接卡带 **`wake=False`**：接收方**只登记、不唤醒**，不得据此再开一轮
  「修复 → 复评」（`SecretarySession.create_handoff(wake=True)` 在熔断会话直接
  抛 `RuntimeError`，不存在误唤醒路径）；
- 卡面附熔断原因 + 轮次/预算快照，接收方 `inherit_silent_handoff()` 起手即熔断
  （轮次计数继承，**换 agent 不重置预算**）；
- 恢复只走**人工解锁** `resume_loop(by=…, reason=…)`（留痕，禁止匿名复活）；
  上游可 `fuse_loop(reason)` 直接叫停。

### 回转卡口径更正

| 项 | 回转（唤醒修复） | 结转（登记不修） |
|---|---|---|
| 🔴 门禁必修 | ✅ 计入门禁预算（默认 3） | ❌ 不可结转 |
| 🟡 非门禁建议 | ✅ **仅第 1 次** | ✅ 第 2 次起**一律结转**，随静默交接交接出去 |
| 🟢 优化 | ❌ | ✅ 登记 |

> 落地代码：`state-secretary/src/secretary/loop/loop_guard.py`（`LoopGuard`），
> 设计见 `docs/design/state-secretary-loop-guard.md`。

## 2.2 评审版本仲裁（v0.4 新增 · Ref: #14）

评审期间"开发还在改"是常态，但**不能因此阻塞评审**（"不要让一个小冲突影响整体"）。
写回机制四步：

| 步骤 | 口径 | 行为 |
|---|---|---|
| 1 | **只在开启评审时记录版本** | 开发过程不记；`begin_review()` 才登记基线（幂等，不偷偷推前） |
| 2 | **无法追踪变化就以新的** | 基线缺失/版本退化/无共同祖先 → `REBASE`，不编造冲突 |
| 3 | **正在编辑 → 防同写锁 + 延迟** | 他人写租约 → 本次不落盘，等 `retry_delay_sec`（默认 30s）后重试 |
| 4 | **先完成该做的，只额外处理一个** | 评审**先落盘**；冲突收敛为**一张**卡，后续冲突合并进同一张 |

- 🔴 **冲突不阻塞评审**：`applied=True`，评审结果照常落盘；
- 🔴 **待处理冲突卡至多一张**：连续 N 次冲突仍是 1 张（`merged_conflicts` 累加），
  不会"每轮各开一张票"再形成循环；
- 🔴 **冲突不消耗轮次预算**：`LoopGuard` 的修复轮次只统计"修复往返"，冲突另计；
- 收口：`resolve_review_conflict(id, resolution, by=…)`（留痕），收口后基线以当前
  版本重立，后续**从新版本继续**（不因一次冲突重开全量）。

> 参照物口径（易踩）：判"对方是否有效推进"必须拿**评审基线快照**比，
> 不能拿"开始写回时的最新卡"比——后者已含对方变更，互比恒为"无进展"→ 每次并发
> 都误判冲突。落地见 `ReviewBaseline.history` 与 `ReviewArbiter._is_progress`。

## 2.3 审查范围分级（v0.4 新增 · Ref: #14）

> 不要这样大量全量——**只在大版本可以进行全量**，日常开发**只审查变化**，
> 防止无效构建和测试。

| 档位 | 触发 | 构建/测试口径 |
|---|---|---|
| `full` | 大版本标签（`major-version` 等）/ 大版本文本信号 / 显式 `major_version=True` | 全量构建 + 全量测试 |
| `scan` | **其余全部情形**（默认） | 仅变更包/目标 + 仅变更相关用例与受影响面，**不跑全量** |

- **拿不准就不全量**：默认降级 `scan`；显式"只审变化/增量"**优先于**大版本信号。
- 增量优先**不减少验收强度**：🔴 门禁项的验证要求不变，只是不再重跑全量。
- 落地：`review/scope.py`（`decide_scan` / `scan_commands`）；
  门面 `SecretarySession.review_scope()` / `review_scope_commands()`。

## 3. 角色职责与交接卡

| 角色 | 职责 | 交接/回转条件 |
|------|------|-------------|
| 秘书·开发 | 需求实现、测试全覆盖、POC 落地 | 按状态管理秘书拆解任务实现；提 PR 前过标准检查 |
| 秘书·评审 | 合规评审、契约绑定处置标签 | 发现 🔴 必修 → `[回转] 退回:秘书·开发` |
| 秘书·测试 | 按验收标准逐项验证 | 仅接收「开发自评无问题」的任务；发现缺陷 → `[回转]` |
| 秘书·交付 | （后续扩展）最终交付人确认 | 评审最终放行后进入 |

### 交接卡格式（[触发:<角色>] 接力）

```
[触发:秘书·测试]
- 接力来源：秘书·开发（自评 ✅ 无问题）
- 验收对象：<PR/Issue #编号> <模块/范围>
- 待验证要点：<具体事项列表>
- 请校验并回执
```

### 回转卡格式（[回转] 退回）

```
[回转] 退回:秘书·开发
- 原因：🔴 必修项未清零 / 测试发现 P0 缺陷
- 下一步要求：<定点修 diff 即可 / 需整 PR 重构>
- 修正后回我复评
- 轮次：第 N / 3 轮（门禁预算）；🟡 项仅第 1 次可回转，其后结转
- 审查范围：`scan`（只审变化，默认）/ `full`（仅大版本）
```

### 熔断交接卡格式（静默 · 不唤醒）

```
[静默交接] wake=False · 不唤醒
- 熔断原因：非必要修复已达上界 1 次 / 门禁修复轮次已达上界 3 / 停滞循环（同一指纹 N 次）
- 轮次快照：total / blocking_rounds / repair_rounds / advisory_used / stall_count
- 接收方动作：**只登记，不唤醒**；不得据此再开一轮「修复 → 复评」
- 待办结转：<🟡 项清单>（登记入 Issue 台账，不占本轮修复）
- 恢复途径：仅人工 `resume(by=…, reason=…)`
```

## 4. 状态机映射

- 每个交付物（PR/文档/模块）的状态流转对齐 TaskState：
  - `todo` → 分配开发
  - `in_progress` → 开发中
  - `done` → 开发自评通过
  - `blocked` → 评审/测试发现阻塞缺陷（回转）
  - `stopped` → 归档/放弃追踪
  - 合并放行 = 最终评审通过 → 人工 merge
