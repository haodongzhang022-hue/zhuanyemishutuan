# 秘书协作门禁流转规范

> version: v0.10（新增 §2.2.3 平台语义对齐 + §2.5 评审项去重与能力降级 · Ref: #14 本轮）
> module: zhuanyemishutuan · docs
> Ref: #1 · PR #2 · #14

## 1. 目的

明确定义秘书团「开发 → 评审 → 测试 → 合并前最终评审」的门禁流转规则，替代早期「评审通过即接力测试」的不闭环流程。
v0.3（Ref: #14）为门禁往返加**上界**：轮次预算 + 非必要修复最多 1 次 + 停滞感知 + 静默交接不唤醒（§2.1）。
v0.4（Ref: #14）补**评审写回机制**：只在开启评审时记版本 + 防同写锁 + 延迟重试 + 单冲突收口（§2.2），
并加**审查范围分级**——日常只审变化、全量只在大版本（§2.3）。
v0.5（Ref: #14 追问）把**等待节奏**改为**阶梯**（10s→30s→60s→3min→6min→10min **到顶即停**），
并把整包协同参数抽成**全局跨仓库规则**（§2.2.1 + `docs/secretary-collab-rules.md`）；
同时明确**等待不计 CPU**（平台挂起语义，本地不做空转）。
v0.6（Ref: #14 追问）把"等"改成**非轮询检查点探测**（§2.2.2）：形成检查点 → 判断检查点 →
状态变化/到点再触发，最多 6 次。
**v0.10（Ref: #14 本轮）对齐官方平台语义 + 官方最佳实践**（§2.2.3 + §2.2.4）：
`cnb:await` 的「**同一事件**才能配对」「一个 key **仅能 resolve 一次**」两条硬约束
此前未落地（会导致 await **永远等不到**）→ 现在挂之前先校验、配不上对就降级 `crontab`，
await key 按轮次唯一；同时补**评审项确定性去重**（同一问题不报第二遍）与
**能力降级保守放行**（判不出影响面就不做增量判重）。

## 2. 门禁流转（v0.2 新机制 · v0.3 加熔断上界见 §2.1）

```
┌──────────┐     发现问题/缺陷      ┌──────────┐
│ 秘书·开发 │ ────[回转]────────▶ │ 秘书·评审 │
│          │ ◀───[返工修正]──────── │          │
└──────────┘                      └──────────┘
     │ ▲
     │ │ 开发自评OK
     ▼ │ 只有确认无问题才接测试
┌──────────┐     发现缺陷      ┌──────────┐
│ 秘书·测试 │ ───[回转]─────▶ │ 秘书·开发 │
└──────────┘                  └──────────┘
     │
     │ 测试通过
     ▼
┌──────────┐    合并前最终评审     ┌──────────┐
│ 秘书·评审 │ ◀──────────────────── │          │
└──────────┘                       │ 合并放行 │
                                   └──────────┘
```

### 核心规则

1. **评审发现问题 → 回开发修正**（不直接放行接测试）
2. **开发修完、自评无问题 → 才接测试**
3. **明知还有问题 → 不接测试，回开发调整**
4. **准备合并之前 → 走最终评审放行**

## 2.1 循环熔断（v0.3 新增 · Ref: #14）

门禁往返本身也需上界，否则「打回 → 修正 → 复评」会无限循环。三道（+1）上界：

| 上界 | 默认 | 口径 |
|---|---|---|
| 门禁修复轮次 | 3 | 🔴 必修项回转为一次修复；耗尽即熔断 |
| **非必要修复轮次** | **1** | 🟡 建议项**最多修 1 次**；再报同类**不作回转**，改**结转登记** |
| 修复总轮次 | 5 | 防 🔴/🟡 交替出现绕过前两道 |
| 停滞重复 | 2 | 同一整改项指纹连续出现 2 次且无进展 → 判停滞循环，立即熔断 |

**判定顺序**：已熔断 → 停滞 → 总轮次 → 门禁 → 非必要 → 无需修复（`clear`，不耗预算）。
`clear`（既无 🔴 也无 🟡）不消耗任何预算、不唤醒。

### 熔断后：静默交接（不唤醒）

- 交接卡带 **`wake=False`**：接收方**只登记、不唤醒**，不得据此再开一轮
  「修复 → 复评」（`SecretarySession.create_handoff(wake=True)` 在熔断会话直接
  抛 `RuntimeError`，不存在误唤醒路径）；
- 卡面附熔断原因 + 轮次/预算快照，接收方 `inherit_silent_handoff()` 起手即熔断
  （轮次计数继承，**换 agent 不重置预算**）；
- 恢复只走**人工解锁** `resume_loop(by=…, reason=…)`（留痕，禁止匿名复活）；
  上游可 `fuse_loop(reason)` 直接叫停。

### 回转卡口径更正

| 项 | 回转（唤醒修复） | 结转（登记不修） |
|---|---|---|
| 🔴 门禁必修 | ✅ 计入门禁预算（默认 3） | ❌ 不可结转 |
| 🟡 非门禁建议 | ✅ **仅第 1 次** | ✅ 第 2 次起**一律结转**，随静默交接交接出去 |
| 🟢 优化 | ❌ | ✅ 登记 |

> 落地代码：`state-secretary/src/secretary/loop/loop_guard.py`（`LoopGuard`），
> 设计见 `docs/design/state-secretary-loop-guard.md`。

## 2.2 评审版本仲裁（v0.4 新增 · Ref: #14）

评审期间"开发还在改"是常态，但**不能因此阻塞评审**（"不要让一个小冲突影响整体"）。
写回机制四步：

| 步骤 | 口径 | 行为 |
|---|---|---|
| 1 | **只在开启评审时记录版本** | 开发过程不记；`begin_review()` 才登记基线（幂等，不偷偷推前） |
| 2 | **无法追踪变化就以新的** | 基线缺失/版本退化/无共同祖先 → `REBASE`，不编造冲突 |
| 3 | **正在编辑 → 防同写锁 + 延迟** | 他人写租约 → **先做其他，并挂锁**；延迟 **1 分钟**后检测（重触发转 3 分钟持续锁） |
| 4 | **先完成该做的，只额外处理一个** | 评审**先落盘**；冲突收敛为**一张**卡，后续冲突合并进同一张 |

- 🔴 **冲突不阻塞评审**：`applied=True`，评审结果照常落盘；
- 🔴 **待处理冲突卡至多一张**：连续 N 次冲突仍是 1 张（`merged_conflicts` 累加），
  不会"每轮各开一张票"再形成循环；
- 🔴 **冲突不消耗轮次预算**：`LoopGuard` 的修复轮次只统计"修复往返"，冲突另计；
- 收口：`resolve_review_conflict(id, resolution, by=…)`（留痕），收口后基线以当前
  版本重立，后续**从新版本继续**（不因一次冲突重开全量）。

> 参照物口径（易踩）：判"对方是否有效推进"必须拿**评审基线快照**比，
> 不能拿"开始写回时的最新卡"比——后者已含对方变更，互比恒为"无进展"→ 每次并发
> 都误判冲突。落地见 `ReviewBaseline.history` 与 `ReviewArbiter._is_progress`。

## 2.2.1 锁聚合管理 + 等待阶梯（v0.5 · Ref: #14 追问）

> 延迟可以到 **1 分钟**；**再次触发就按 3 分钟持续到对方解决完**；**别遗留锁一直不
> 打开**；**所有锁应该被聚合的管理**，哪里要避开**不用测试才知道**，触发了**看一眼
> 就有数**；触发机制 = **延迟后检测** + **先做其他，并挂锁**。

| # | 口径 | 落地 |
|---|---|---|
| 1 | 延迟窗（阶梯首档） | `StepBackoff` 首档 **10s**（不传参即走阶梯） |
| 2 | 重触发持续到对方解决完 | 重触发即 `persistent`；等待**沿阶梯上行**且只增不减 |
| 3 | 别遗留锁一直不打开 | 每锁必有到期；`sweep_locks()` 回收过期+超宽限；收口/消解即释放 |
| 4 | 所有锁聚合管理 | 一本台账 `<数据根>/locks/registry.json`（写租约 / 评审读锁 / 延迟锁） |
| 5 | 触发即可查看 | `locks_overview()` 的 `where_to_avoid`：谁锁的、锁什么、还有多久 |
| 6 | 延迟后检测 + 先做其他并挂锁 | `retry_review()` 到点检测；`deferred_review_status()` 看挂账项 |

### 等待阶梯（v0.5 改口径 · 从少到多，到顶即停）

> 从少到多符合逻辑，因为**大部分都是很快就没问题了**——第一次 **10 秒**，然后
> **30 秒、60 秒、3 分钟、6 分钟**，持续增加到 **10 分钟就停止**。

| 第几次检测 | 1 | 2 | 3 | 4 | 5 | 6 及以后 |
|---|---|---|---|---|---|---|
| 等待 | **10s** | 30s | 60s | 3min | 6min | **10min（顶，停）** |

- **从少到多**是定值阶梯（不是倍率推算）；**前两档很短**：多数冲突第 1 次检测就没了；
- **到顶即停**：10 分钟之后**不再增长**，到顶次数用尽 → `resume_required`
  （**停止自动挂账，交回人工/上游**，不拖着一个永不结束的会话）；
- **只增不减**：重触发不得把已承诺的长等待改回短档；
- 原「60 → 120 → 180 封顶」口径**作废**（那是旧退避；3 分钟现在是阶梯中的一档）。

### 等待不计 CPU（v0.5 明确 · 回答"会不会占用构建 CPU 计费"）

- 平台计费项只有 **CPU 核时**（按任务实际运行时长，每 5min 冻结 `5min × 节点规格`）
  与 **AI Credits**（按模型调用 Token）——**没有「等待」这一项**；
- 前提是等待走**平台挂起语义**（如 `cnb:await`）；本地 `sleep` / 空转轮询才在烧核时
  （8 核空转 10 分钟 ≈ 1.33 核时 ≈ ¥0.17）；
- 故等待模式只有三种：`platform_suspend`（挂平台等）/ `deferred_review`（先做其他）/
  `resume_required`（到顶交回人工）——**永不选"本地空转"**。

### 其余口径

- 四种锁：`card_write`（正在编辑）/ `review`（评审读锁）/ `defer`（延迟锁）/
  `serialize`（写入序列化）；
- **单锁兼容**：`<session>.owner.json` 仍是终态判据，台账只是镜像 + 聚合视图，
  台账坏了不影响加锁语义；
- 持续锁在宽限内 `should_release()` 恒 `False`——**不许提前打开**；
- 收尾：`complete_deferred_review()`；释放：`release_review_locks()`。

> 整包参数（阶梯 / 锁 / 熔断 / 审查范围 / 计费口径）抽为**全局跨仓库规则**：
> `shared/collab/collab-rules.yaml`，见 `docs/secretary-collab-rules.md`。
> 门面：`collab_status() / waiting_plan() / waiting_status() / wait_decision() / cost_note()`。
> 设计详见 `docs/design/state-secretary-lock-registry.md`。
> 落地：`collab/backoff.py` + `collab/wait_policy.py` ＋ `state/lock_registry.py`
> ＋ `review/review_arbiter.py`（阶梯接线）

## 2.2.2 检查点探测（v0.6 新增 · Ref: #14 追问）

> **最多 6 次就行**，再多就不适合等待了，不是这里的问题了，或者我们是否可以以
> **非轮询**而是**形成检查点然后 webhook 触发再跑**，**等他的锁**，然后形成一个机制
> **判断检查点**，类似于**边缘计算的探测器**这样的，会不会好点。怎么处理比较好，
> 平台对这个有最佳实践吗。

| # | 口径 | 落地 |
|---|---|---|
| 1 | **最多 6 次** | 探测上界 = 等待阶梯档位数（6）；用尽 → `resume_required`，**停止自动挂账** |
| 2 | **非轮询** | 落点只有平台语义：`cnb:await`（≤5min，零占用）/ `crontab`（>5min，平台代跑）/ `api_trigger`（外部 webhook 再跑）/ 交回人工 |
| 3 | **形成检查点 → 判断检查点** | `create_checkpoint(key, kind, holder, scope)` → `probe_checkpoint(key)` |
| 4 | **等他的锁** | 判别式 `lock`：锁快照可见且被持有 → `wait`；锁释放 → `proceed`；**锁表不可见 → `unknown`**（不误判） |
| 5 | **边缘计算的探测器** | 本地只做**轻量采集 + 判定**，产出 `ProbeEvent`（结构化事件）；重活（评审/构建/模型）只在 `proceed` 时才做 |
| 6 | **反队头阻塞** | `our_need_satisfied=False`（我方已不需要）→ 直接 `release`：**放锁、不再等** |

### 判别式与判定（确定性，不看 agent 自述）

| `kind` | 事实 | `proceed` | `wait` | `unknown` |
|---|---|---|---|---|
| `confirm` | `confirmed` | True | False | 未给事实 |
| `lock` | 锁表快照 | 锁已释放 | 锁仍被持有 | 锁表不可见（未接入台账） |
| `version` | 版本号（**探测前快照**为参照） | 版本变化 | 版本未变 | 首次采集，无基线 |
| `event` | `event_fired` / 平台 `resolve` | 事件已到达 | 尚未到达 | 无信号 |
| `resource` | `resource_ready` | 已就绪 | 未就绪 | 信号缺失 |

- 判定顺序：**我方是否还需要 → 判别式事实**；`unknown` 的处置恒为"继续等"，
  **绝不**降级成"放行"；
- **自述不入判定**：`agent_says_done` 之类字段既不采集也不采信。

### 平台最佳实践（官方文档口径）

| 能力 | 平台机制 | 文档 |
|---|---|---|
| 一次探测 = 一次事件，**零占用** | `cnb:await` / `cnb:resolve`：pipeline 执行到 await 即挂起，由**状态变化**唤醒（同一事件内配对） | `/zh/build/internal-steps/cnb/await-resolve.md` |
| 延迟兜底（**平台是那个"不睡觉的进程"**） | `crontab` 定时任务，**最小间隔 5 分钟**，触发 `api_trigger_probe_check` | `/zh/build/crontab.md` |
| 外部 webhook / 调度系统再跑 | OPENAPI `StartBuild` 触发 `api_trigger` 流水线（官方推荐跨根组织场景） | `/zh/build/trigger-rule.md` |
| 跨流水线/跨仓再触发 | `cnb:apply`（同仓）/ `cnb:trigger`（跨仓）触发 `api_trigger_*` | `/zh/build/internal-steps/cnb/trigger.md` |
| **等待不计费** | 计费只有 CPU 核时（实际运行时长）+ AI Credits（Token），**无"等待"项** | `/zh/pricing.md`、`/zh/build/timeout.md` |

**结论（三条最佳实践）**：① 等锁首选 **`cnb:await` 平台挂起**——这才是"webhook
触发再跑"在 CNB 上的原生形态；② 若锁由**仓库外**持有者（如正在编辑的真人）把持、
平台内没有"锁释放事件"可等，就用**平台定时任务**到点代跑探测；③ **本地永不
sleep/轮询**——那是唯一真正烧核时的做法。

> 门面：`create_checkpoint() / checkpoint_plan() / register_platform_wait() /
> probe_checkpoint() / dispatch_probe_event() / checkpoints_overview() / probe_status()`。
> 规则包：`shared/collab/collab-rules.yaml` 的 `probe` 段；设计见
> `docs/design/state-secretary-checkpoint-probe.md`；落地 `collab/probe.py`。

### 三点已确认（v0.7 · 固化）

| # | 确认项 | 固化口径 |
|---|---|---|
| 1 | 落点分工「≤5min 挂 `await`，>5min 交 `crontab`」 | **硬口径**，按 `probe.await_max_sec`（默认 300s）自动分工；**不存在"一律挂 await"的回退路径**；两落点互斥（await 行不带 cron，crontab 行必带） |
| 2 | `cron` 间隔「**固定 `*/5` 一档扫**」 | 所有平台定时探测点统一 `*/5 * * * *`，**不随阶梯档位放大**（旧 `*/6`、`*/10` 作废）；与阶梯时间表解耦 |
| 3 | `probe` 规则「**推到组织级共享**」 | 装载层级 **组织级 → 仓库级（只覆写数值）→ 内置默认**；仓库级改不动语义；跨仓事件按判定字符串出同一套动作 |

> 跨仓接力时**只传判定**（`wait` / `proceed` / `release` / `unknown`），接收方用
> `dispatch_shared()` 按组织级规则算落点——**不按自己的本地会话号重算**，
> 也不会因为辨识不出对方的检查点而误判放行（非法判定一律 `unknown` → 继续等）。

## 2.2.3 平台语义对齐（v0.10 新增 · Ref: #14 本轮）

> 官方有没有对此有最佳实践可以参考过来。

**方向对了，但"抽象的落点"≠"具体任务的真实约束"。** 逐条查证官方文档后，发现
`cnb:await` 有两条**会让落点失效**的硬约束（原文见
`/zh/build/internal-steps/cnb/await-resolve.md`）：

| 官方约束 | 原实现的问题 | 收口（本版） |
|---|---|---|
| 「只能对**同一个事件**触发的 pipeline 进行 await 和 resolve 操作」 | 探测/干活 pipeline 常由 `crontab`/`api_trigger` 触发，放锁方多在 `push`/评论事件 → **配不上对，await 永远等不到** | 挂之前先 `resolve_driver()` 校验；不同事件/不可判定 → **降级 `crontab`**（平台代跑，**且平台会做死锁检测**） |
| 「一个 `key` **仅能 resolve 一次**（可 await 多次）」 | 同一检查点第 4、5 次探测复用同一 key → 第 2 次起**必死等** | await key **按轮次唯一**：`probe:<checkpoint>:r<n>` |
| 「await-resolve 只能运行在流水线的 `stages` 中」（`endStages`/`failStages` 不生效） | 收尾/失败阶段挂 await 会**直接不生效** | 位置校验 `await_stage_ok()` |

**判定口径（保守，判不出就不挂）**：

| 情形 | 落点 |
|---|---|
| 两侧事件**相同** 且位于 `stages` | `platform_await`（零占用，对端 resolve 唤醒） |
| 两侧事件**不同** / **任一不可判定** | **降级** `platform_crontab`（固定 `*/5` 一档扫） |
| 等待方本身是平台定时事件（`crontab`） | 降级（平台到点会再来一次，等它没有意义） |
| 位置在 `endStages` / `failStages` | 降级（官方不生效） |

**降级不等于丢功能**：`crontab` 仍是**平台**在等（平台是那个不睡觉的进程），
本地 CPU 占用恒为 **0**；两处落点都**不允许**本地 sleep/轮询。

**跨仓同理**：对方的检查点**不在本地磁盘上**，故跨仓事件必须**自带**两侧事件名；
没带 → 不猜、保守降级（此前按**本地会话号**读检查点，会读到"别人的/不相干的"状态）。

代码：`secretary/collab/platform.py`；门面 `platform_report()` / `await_eligibility()` /
`await_plan()` / `await_key_of()`；测试 `test_platform_semantics_issue14.py`。

## 2.2.4 评审项去重与能力降级（v0.10 新增 · Ref: #14 本轮）

### 2.2.4.1 同一问题不报第二遍（评审项指纹）

官方对照（`cnbcool/code-review` vs SCA 插件）：

| 官方做法 | 性质 |
|---|---|
| 评审插件 `include_existing_comments`：拉历史评论给模型**参考**，避免重复刷评论 | **模型判断**（本次与上次不一定一致） |
| SCA 插件：「同一组件同一 CVE **不重复阻断**」「**内容未变化的文件重命名不重复产生**」 | **确定性**（硬口径） |

本版把后者的硬口径搬到评审侧：**同一「类别 + 语义锚点」不重复报**。

- **锚点不含路径、不含行号**：改名与整体移位**不算新问题**（否则"同一个问题换个位置"
  就再报一遍 → 多一轮往返，正是要治的循环）；格式噪音（注释/字面量/数字/操作符空白）
  一并归一化。
- **重复项自动结转**：再出现只登记，**不回转、不占轮次**（`should_rotate` 只看新问题）。
- **降噪照抄官方默认**：`exclude_categories: style,nit`、`min_severity` 阈值、
  非代码文件（锁文件/图片/构建产物）过滤——官方验证过的默认值，没必要另立一套。

代码：`secretary/review/fingerprint.py`；门面 `review_dedup()` /
`carry_review_items()` / `review_fingerprints_overview()`。

### 2.2.4.2 能力降级：判不出就不增量（保守放行）

`RunScopeGuard` 的判重依赖**受影响面**。拿不到变更集时（新建分支 push 无上一个
commit / 受影响面为空），空 impact **本身是一个合法指纹** → 不同变更集可能撞成同一个
→ **该跑的被跳过**（漏跑，危险方向）。按官方 SCA 增量口径（"判不出新增就不报增量"）
改为**保守放行**：

| 情形 | 判定 |
|---|---|
| 有版本 + 有具体受影响面 | 正常增量判重 |
| 缺 `revision` / `base` 给空 / `branch.create` | **降级放行** + 留痕（`degraded` / `degrade_reason`） |
| 有 base 但受影响面为空（算出来是空 vs 算不出来无法区分） | **降级放行** |

口径：**漏跑比多跑危险**，故一律取安全一侧。

## 2.3 审查范围分级（v0.4 新增 · Ref: #14）

> 不要这样大量全量——**只在大版本可以进行全量**，日常开发**只审查变化**，
> 防止无效构建和测试。

| 档位 | 触发 | 构建/测试口径 |
|---|---|---|
| `full` | 大版本标签（`major-version` 等）/ 大版本文本信号 / 显式 `major_version=True` | 全量构建 + 全量测试 |
| `scan` | **其余全部情形**（默认） | 仅变更包/目标 + 仅变更相关用例与受影响面，**不跑全量** |

- **拿不准就不全量**：默认降级 `scan`；显式"只审变化/增量"**优先于**大版本信号。
- 增量优先**不减少验收强度**：🔴 门禁项的验证要求不变，只是不再重跑全量。
- 落地：`review/scope.py`（`decide_scan` / `scan_commands`）；
  门面 `SecretarySession.review_scope()` / `review_scope_commands()`。

## 2.4 增量执行与同口径去重（v0.9 新增 · Ref: #14 追问）

> 平时不需要跑全量，而且**尤其**不适合连跑三次…**同一个口径几乎不会产生分歧**。
> 所以像这种连续跑三次全量是无效的。…我们已经把这一套只跑增量、不跑全量的建立过了呀。

**问题定位（用户问"是规则不健全吗？还是配置有问题？"）**：两者都有——

| 缺口 | 表现 | 修法 |
|---|---|---|
| 规则只到"范围"，没到"重复" | 只说了"别全量"，**没说"同一口径别重复跑"** | 规则包补 `max_identical_repeats` / `allow_stability_repeats` / `stability_via` |
| 规则是**口径**不是**机制** | 写给人/agent 看，靠"记得"执行；没人提就不会执行 | 新增 `RunScopeGuard`：判 `skip_duplicate` 即**不跑**（跳过不需要自觉） |
| 配置**白名单漏登记** | 规则文件里写了新字段，**跑起来还是默认值**（静默丢弃） | 补齐 `_OVERRIDABLE_FIELDS` + 自检 `_audit_overridable_fields()` |
| 流水线**没有测试阶段** | `.cnb.yml` 只有 echo/node -v，"只跑增量"无处落地 | 新增 `scripts/ci-incremental-test.sh` 并接入 `main.push` |

**判定表**（`RunScopeGuard.decide`，口径指纹 = `mode + revision + impact + command`）：

| 情形 | 判定 |
|---|---|
| `window_repeats > 1`（想连跑 N 次） | `blocked_stability` —— **红/绿都拒**，给替代口径 |
| 缺版本 / 缺命令 | `run`（判不出就不拦） |
| 同口径次数 < 上界 | `run` |
| 达上界 + 上一轮**明确红** | `run`（红→修→再跑有新信息） |
| 达上界 + 其余（含**没给结论**） | `skip_duplicate` |

- **"没给结论 ≠ 跑红了"**：把未知当红 = 默认放行，判重形同虚设（本轮修掉的真缺陷）。
- **稳定性论证换口径**：定点探针 / 变异探针 / 独立场景，而不是把同一命令再跑两遍
  （跑法固定 → 重复跑**不产生判别力**）。
- 受影响面按**集合**语义（换顺序 = 同一口径），且必须**由 revision 决定**
  （读工作区会算出假新口径 → 判重失效）。
- 落地：`collab/run_guard.py`；门面 `run_decision` / `record_run` / `run_repeats_of` /
  `run_scope_overview` / `run_scope_note`；执行入口 `scripts/ci-incremental-test.sh`。

## 2.5 全量门禁（v0.11 新增 · Ref: #14 本轮追问）

> 这里我要求过不跑全量，他怎么还在一直连续跑三次稳定这种事情？…他不然我们新开发一步，
> 他就要跑一次 600 多次的验证。甚至还要跑三倍，这太过分了。…处理完这个让他合理起来，
> 我们再通用，不然相当于一次污染了很多仓库。

**根因（两条都是"看起来做了、实际拦不住"）**：

| # | 上一轮的做法 | 为什么没拦住 |
|---|---|---|
| 1 | `scan.default_mode: scan` | 是**默认值**，不是**门禁**——显式给 `mode="full"` 直接绕过 |
| 2 | `RunScopeGuard` 判重 | 比较键含 **`revision`**：**改一行代码 revision 就变** → 次次算新口径 → 次次放行 |
| 3 | 各事件共用一套流水线 | 评论/目录/定时类事件也跑测试 → 无基线、无变更集，纯空烧 + 跨仓污染 |

**三道硬闸**：

1. **`decide_full()`**：`full` 必须同时满足「大版本事实 + 可采信来源（action/tag/operator）
   + 代码推进类事件」，否则 `blocked_full` 并给出**可直接跑**的增量命令；
   **agent 自述不算凭据**（否则"喊一声大版本"就能解锁）。
2. **去升级口径 `repeat_scope: content`**：按**受审内容**判重（跨版本），
   修掉"每开发一步重跑一遍"。
3. **事件侧 + 单入口 + 兜底白名单**：评论类事件走接待任务不做测试；
   `scripts/ci-dispatch.sh` 不接收全量参数；兜底只允许改 `shared/collab/`。

**⚠️ 方向性**（必须写进角色口径，否则会被"保守"两个字带偏）：

| 判定 | 判不出 | 安全侧 |
|---|---|---|
| `run_decision`（跳过重复） | **放行** | 漏跑比多跑危险 |
| `full_decision`（全量门禁） | **拦截** | 空烧全量比少跑危险 |

- 落地：`collab/full_gate.py` + `collab/platform.py`；
  门面 `full_decision` / `full_run_eligible` / `pipeline_change_allowed` /
  `full_gate_note` / `decide_repeat` / `record_repeat` / `content_repeats_of`。

| 角色 | 职责 | 交接/回转条件 |
|------|------|-------------|
| 秘书·开发 | 需求实现、测试全覆盖、POC 落地 | 按状态管理秘书拆解任务实现；提 PR 前过标准检查 |

| 秘书·交付 | （后续扩展）最终交付人确认 | 评审最终放行后进入 |

### 交接卡格式（[触发:<角色>] 接力）

```
[触发:秘书·测试]
- 接力来源：秘书·开发（自评 ✅ 无问题）
- 验收对象：<PR/Issue #编号> <模块/范围>
- 待验证要点：<具体事项列表>
- 请校验并回执
```

### 回转卡格式（[回转] 退回）

```
[回转] 退回:秘书·开发
- 原因：🔴 必修项未清零 / 测试发现 P0 缺陷
- 下一步要求：<定点修 diff 即可 / 需整 PR 重构>
- 修正后回我复评
- 轮次：第 N / 3 轮（门禁预算）；🟡 项仅第 1 次可回转，其后结转
- 审查范围：`scan`（只审变化，默认）/ `full`（仅大版本）
- 等待（若卡正在被编辑）：第 N 档 / 阶梯 `10s→30s→60s→3min→6min→10min`（到顶即停）
- 落点分工：≤5min 挂 `cnb:await`（零占用、事件唤醒）；>5min 交平台 `crontab`（**固定 `*/5` 一档扫**）
- 计费口径：等待走**平台挂起**，不计构建 CPU；本地不做 sleep/轮询
```

### 熔断交接卡格式（静默 · 不唤醒）

```
[静默交接] wake=False · 不唤醒
- 熔断原因：非必要修复已达上界 1 次 / 门禁修复轮次已达上界 3 / 停滞循环（同一指纹 N 次）
- 轮次快照：total / blocking_rounds / repair_rounds / advisory_used / stall_count
- 接收方动作：**只登记，不唤醒**；不得据此再开一轮「修复 → 复评」
- 待办结转：<🟡 项清单>（登记入 Issue 台账，不占本轮修复）
- 恢复途径：仅人工 `resume(by=…, reason=…)`
```

## 4. 状态机映射

- 每个交付物（PR/文档/模块）的状态流转对齐 TaskState：
  - `todo` → 分配开发
  - `in_progress` → 开发中
  - `done` → 开发自评通过
  - `blocked` → 评审/测试发现阻塞缺陷（回转）
  - `stopped` → 归档/放弃追踪
  - 合并放行 = 最终评审通过 → 人工 merge
