# ISSUE-001 状态管理秘书机制（层级状态管理 + 上下文折叠编号检索）

> module: zhuanyemishutuan
> version: 0.1.0
> type: feature
> target: 通用层会话编排机制（状态管理秘书）
> depends_on: 无（新仓库初始需求）

## 背景与目标 Y

参考论文 EMNLP26 SKILL.state ——《Scalable Long-Horizon Agent Skills》（https://arxiv.org/abs/2608.26263）：
- 论文核心：用「技能说明 + 当前结构化状态 + 最新观察」驱动每一步执行，校验状态补丁后丢弃本步推理，避免持续追加历史导致 prompt 无限变长、旧动作与无关观察干扰模型判断。
- 长程成本：Warehouse 200 步任务，Memory 基线 6,175,509 token vs SKILL.state 122,384 token；分数 0.84 vs 0.94；加 50 个无关事件仍 0.98。
- 关键对照：输入同样短时，截断/摘要/统计压缩得分明显低于结构化状态 → 核心不是单纯减少文字，而是「结构化 + 索引化 + 分层隔离」。
- 论文限制：依赖提前设计的领域状态 Schema；多 Agent 并发写状态需确定性冲突处理。

**本需求是对 SKILL.state 的三处升级（秘书系统改进版）：**

| SKILL.state（论文） | 本方案改进 | 目的 |
|---|---|---|
| 校验后丢弃本步推理 | 保留原文，按任务折叠 + 编号 | 缺原文时可通过索引找回，不丢上下文 |
| 状态由单一 agent 管理 | 层级秘书层层向上提交 | 每层只掌握该层有效上下文，隔离噪声 |
| 状态模式预先设计固定字段 | 按对话/任务动态分配 agent 秘书管理 | 每个 Issue/对话独享独立环境，提示词稳定 |

设计原则：**不是「减少信息量」，而是「结构化信息 + 索引化存储 + 分层隔离」**。

## 用户故事与验收标准

### US-1 层级状态管理秘书
- As 平台编排者，I want 每个 Issue/对话分配一个独立 agent 秘书管理该会话状态，So that 上下文与执行分离。
- 验收：新 Issue/对话创建 → 自动分配独立 agent 秘书，独立管理该会话状态，不与其他会话共享上下文。

### US-2 上下文折叠与编号检索
- As 平台编排者，I want 原始上下文按任务折叠并编号，So that 每段上下文唯一可检索，需要时精确检索而非全文携带。
- 验收：多轮上下文累积 → 秘书折叠为带编号索引的状态；原始文本保留但不常驻 prompt；缺原文时按索引精确检索恢复。

### US-3 层级向上提交
- As 平台编排者，I want 秘书将管理状态向上级 agent 层层提交，So that 上级掌握宏观进度而不被下级细节干扰。
- 验收：下级提交的仅为汇总结构化状态（进度/关键决策/开放项），不携带原始全文；上级状态不含下级无关的其他项目上下文。

### US-4 缓存命中率保障
- As 平台编排者，I want 秘书机制保证同一对话提示词前缀稳定，So that 缓存命中率高、成本低。
- 验收：同一对话多次执行 → 提示词前缀稳定不随对话长度漂移；折叠与编号不破坏前缀稳定。

## 需求澄清结论（用户已答复，直接采信，不再追问）

### Q1 层级定义（人机交互秘书 → 秘书长 → 状态管理秘书 → 会话秘书）
- **人机交互秘书**：与人类交接进度，承接需求交给秘书长安排。
- **秘书长**：各秘书向他汇报，他分析安排，类经理角色，但管理的是秘书团队。
- **状态管理秘书**：相当于小组长秘书，管理分区功能域下的秘书们。
- **会话/对话秘书**：每个 Issue/PR/对话分配一个负责的秘书，责任到人（agent），工作安排与进度检查均有专职。
- 对话内同一任务不分级（防止过度参与冗余）；开发线 = 开发小组开发+评审循环 + 会话秘书状态机 + 偶尔经理/架构师分配任务。
- 秘书长不进入具体对话（将在外军令有所不受，前线懂一手信息；除非架构/任务偏移需干预）。
- 待明确：层级是否对应 M5 交接总线？层级边界与升降规则需架构师设计时定义。

### Q2 折叠触发条件（自动化优先，默认不 AI 评估）
- 折叠 = 开发时一开始就按任务折叠（类 todolist），**不是做完折叠，而是一开始就按任务折叠**，非需要展开默认折叠 → 防 UI 跳变。
- 开发内容归类到某任务下 → 自动折叠；任务结束且不再追踪 → 自动停止追踪。
- 默认大部分走自动，有疑问才问（不是每步 AI 评估）→ 保证秘书上下文纯净、能力充足。
- todolist/任务小目标 为状态机对话管理秘书需要知道的内容——状态管理基本在这个层级，不是展开的全文。

### Q3 原文存储与可读性
- 原始原文自然存在于原始对话内，**不需要额外存储**；只存储二次管理的 todolist/任务小目标（精简信息层，交给状态机秘书驱动下一轮对话）。
- 对话可新开承接新状态任务，或做几步再新开，几次后归档——以效果好为准；末端 agent 不因对话归档而新开 agent 管理状态，可维持到任务结束。
- 需要设计：防止常驻 agent（如秘书长）上下文无限增长的机制——即使依赖助理的状态管理，助理状态也会持续增长，需在合适时机选择丢弃哪些。

### Q4 状态最小 Schema（通用 + 领域扩展）
- 论文要求按领域预定义字段；本方案更通用：通用最小集（如 task_id/progress/decisions/open_items 等字段）所有秘书遵守，允许行业自定义扩展。
- 其他库已按领域划分（本库=秘书/协作领域；另有金融/游戏/视频/小说/电商等），秘书系统参考 https://cnb.cool/dongdongxiaozu/dongjiagoushi（架构师库）既有通用规则。
- 待研究：哪些适合放入通用层、哪些持续演进、哪些迭代后固化到角色/领域词。

### Q5 落库位置
- **新增模块**（功能较多，确保这部分开发纯净可用），不塞进现有模块。

## 范围边界

### In Scope
- 秘书角色状态管理职责模型（状态字段、层级关系、折叠规则）
- 上下文编号与索引机制（编号规则、检索方式、原文存储位置）
- 层级向上提交的状态汇总协议（上级看到的 vs 下级维护的）
- 秘书机制缓存保障策略（与稳定前缀衔接）
- 可验证 POC：单会话多次任务，秘书管理状态 vs 全量历史，对比 token 消耗与缓存命中

### Out of Scope
- 不做 SKILL.state 论文的领域状态 Schema 本体（flag/假设/活动文件等）——那是具体行业内部的
- 不替代 dongjiagoushi 仓库已有秘书协作机制——本仓库只做通用层状态管理秘书抽象
- 不做提示词工程的具体内容优化（各行业单元自治）
- 不处理多 Agent 并发写同一状态的冲突解决（论文标注限制；当前以每对话独立秘书规避）
