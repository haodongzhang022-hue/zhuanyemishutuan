# M1/M2/M8 多行业单元路由POC (R6) · 收编单元为原子
> 架构·经理 | 本仓库定位=通用能力层(跨行业路由/索引/编排), 单元(行业)内部实现归各自源仓

## 背景
用户口径: 本仓库是「通用能力层 / 统一框架」, 负责**索引与路由到各行业单元(如 dongjiagoushi 独立仓)**, 不在本仓重建行业内部细节。
R4/R5 已验证**单单元**内 单直连 + 复合路由。R6 补**跨行业单元**识别与路由。

## 关键设计(守用户口径)
- **收编行业单元为原子**: 本层只持 `unit-index.yaml` **路由索引**(单元能力入口描述), 不触碰任何源仓。
- 本仓库 = 承载+路由索引 + 编排; 各行业实现归各单元仓(如 dongjiagoushi)。真需改源仓 → 到对应仓提 issue, 不在本仓内实现。
- 第二单元(game-dev-example)仅作路由描述**预埋样例**, repo_ref 待真实接入, 不伪造其源仓实现。

## 运行
```bash
cd poc
./m3_multiunit_router.sh unit-index.yaml "<一句话意图>"
```

## 验证结果
| 测试 | 输入 | 路由结果 | 正确 |
|------|------|---------|------|
| D1 | 需要软件研发团队的架构方案设计 | → dongjiagoushi(软件研发) | ✅ |
| D2 | 做一个吃鸡游戏的关卡设计 | → game-dev-example(游戏研发) | ✅ 索引命中(未触碰源仓) |
| D3 | 帮我点个外卖 | 回落 L2 人工确认 | ✅ 置信兜底保持 |

## 结论
1. **跨行业单元路由可行**: 本层以本地索引把多个行业单元作为原子收编, 意图→单元路由命中。
2. **收编原子化成立**: 单元仓库(源仓)不改, 仅其能力入口描述入库, 符合用户「本仓只做承载+路由」口径。
3. **M8 跨行业能力索引预埋**: unit-index 的 capability_tags 即 M8 可检索索引雏形。
4. **人工两头化保持**: 命中直接路由(0人工), 无命中才回落 L2 一次确认。
5. **复合/交接升级(R7)**: 跨行业复合诉求 = 拆子任务 → 各路由到对应单元 → 交接卡汇合(触发对应单元源仓 issue)。属跨库协作, 交接卡协议复用 dongjiagoushi 基座 Relay。

## 技术栈结论(延续)
- 仍是 bash/awk + YAML 索引, 多单元识别可用「先索引级→再单元内岗位级」两级判定, 无需重运行时。
